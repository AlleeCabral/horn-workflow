# HornFlow architecture decision records

Format: problem → alternatives → decision → consequences → validation.

## ADR-0001 — Wrap, do not rewrite, the validated acoustic core
**Problem.** The Webster/LE core passes 147 checks and reconciles with AKABAK BEM
to 0.02 %; a rewrite risks silent physics drift.
**Alternatives.** (a) reimplement inside new abstractions; (b) wrap the existing
modules behind interfaces.
**Decision.** (b). `theory.py`, `response.py`, `mesh.py`, `bem.py`, `build.py`,
`report.py` are unchanged; `physics/solvers/webster.py` and `akabak.py` are thin
adapters that normalise their outputs.
**Consequences.** Zero physics regression risk; slight indirection cost.
**Validation.** `tests/test_baseline.py` freezes the JBL reference numbers and a
byte-identical `curves.csv`; `tests/test_theory.py` (147) still passes.

## ADR-0002 — Standard-library domain state, not a schema library
**Problem.** The state must be versioned, typed and migratable.
**Alternatives.** (a) Pydantic (already present); (b) stdlib `dataclasses`.
**Decision.** (b). The user's dependency policy asks for a lean production path;
`domain/state.py` is `dataclasses` + explicit `to_dict`/`from_dict` +
`MIGRATIONS`.
**Consequences.** No new production dependency; migrations are explicit; JSON
schema is generated by hand if ever needed.
**Validation.** `tests/test_domain.py::test_state_roundtrip_and_stage_status`,
`::test_state_rejects_unknown_schema_version`.

## ADR-0003 — Expected infeasibility is data, not an exception
**Problem.** Impossible geometry is a normal engineering outcome.
**Decision.** Stages return a typed `StageFailure`
(category / failed_checks / affected_candidates / recoverability /
recommended_upstream_revision / evidence). Exceptions are reserved for
programming, dependency and data-integrity errors.
**Validation.** `test_fold_mfg.py::test_ufold_golden_and_selfintersection_flagged`;
the orchestrator marks the stage `failed` and blocks downstream stages.

## ADR-0004 — Stdlib-first artifact writers, honest deferrals
**Problem.** No `trimesh`/`meshio`/`gmsh`/`pyvista`/`vtk`/CadQuery installed.
**Decision.** Implement reliable formats directly (STL via the existing writer,
DXF via the existing writer, **GLB** written from scratch). Formats that need a
CAD/CAM kernel (STEP, 3MF, VTU) are **deferred stubs** that write a
`.DEFERRED.txt` note with the reason — never a dubious hand-rolled file.
**Consequences.** Interchange is real for geometry/viz; editable B-rep STEP is a
future milestone.
**Validation.** `test_fold_mfg.py::test_additive_shell_is_watertight` asserts the
`deferred` list; GLB is validated structurally (magic/version/chunks/meshes).

## ADR-0005 — Folded horn preferred, not privileged
**Problem.** The spec wants folding preferred but fair.
**Decision.** A configurable `registry.PREFERENCE_BONUS` (folded_horn +0.05 to a
0–100 score) is applied **after** hard gates. The critic
(`critique.critic._preference_check`) fails if the folded horn wins *only*
because of the bonus.
**Validation.** `test_pipeline.py` + Appendix A of the report.

## ADR-0006 — Rotation-minimizing frame over Frenet
**Problem.** Swept cross-sections need a stable local frame.
**Decision.** Double-reflection RMF (Wang et al. 2008) so straight runs and
zero-curvature transitions do not flip the frame.
**Validation.** `test_domain.py::test_rmf_is_orthonormal_and_finite_on_straight`.

## ADR-0007 — Exact centreline length under folding
**Problem.** Arc chord discretisation shortened the path (~0.036 mm over 1.5 m).
**Decision.** Size the legs from the arc's *polyline* length so the realised
centreline length equals L exactly.
**Validation.** `test_fold_mfg.py::test_jfold_golden` (length within 1e-6 m).

## ADR-0008 — New package is `reporting`, not `report`
**Problem.** `hornflow/report.py` already exists (legacy CLI). A `report/`
package would shadow it and break the existing command.
**Decision.** Name the new package `hornflow.reporting`.
**Validation.** `python3 run_workflow.py …` still works; `import hornflow.report`
resolves to the legacy module.

## ADR-0009 — Offline Three.js viewer (classic r128 build)
**Problem.** ES-module three.js cannot load from `file://` (module CORS).
**Decision.** Vendor the classic (non-module) three.js r128 builds and embed the
GLB as base64 in a self-contained `viewer.html`, so it opens with no server and
no network. Three.js is MIT; see
`hornflow/viz/viewer/vendor/LICENSE-thirdparty.txt`.
**Validation.** GLB structural check; the viewer is a static asset (manual open).

## ADR-0010 — Dependency policy
Production: numpy, scipy, PyYAML, matplotlib (`requirements.txt`). Test-only:
pytest, hypothesis (`requirements-dev.txt`). Optional, approval-gated:
pyarrow/trimesh/meshio/gmsh/pyvista/vtk/CadQuery (`requirements-optional.txt`).

## ADR-0011 — The UI is local-first: the viewer becomes the app shell (no Jira)
**Problem.** The first UI layer must let one real run be executed end to end,
including the manual AKABAK checkpoint and the `.vips` import. Two candidate
directions were designed: a Jira issue panel (later a Forge Custom UI app), and a
local app built on the existing offline viewer.
**Alternatives.** (a) Jira/Forge: rich workflow and assignment, but Forge resolvers
cannot run a shell or touch a filesystem, so the pipeline needs a separate runner
service, plus admin work for fields and scopes — a lot of machinery before a single
run exists. (b) Local-first: extend the viewer we already ship into a multi-tab
page, read the run's own artifacts, and add a stdlib `http.server` for the mutating
actions.
**Decision.** (b). The existing viewer **becomes the app shell** and is the Viewer
tab; a Workflow tab is added beside it (plus a Results placeholder). The UI is a
**renderer of a HornFlow-emitted view model** (`app_view.json`); all mutations go
through HornFlow functions (`run_pipeline`, `bem_import.import_into_run`) so
`state.json` stays authoritative. The Jira/Forge designs are kept as documents but
their hosting decisions are superseded.
**Consequences.** One command to a working UI on any machine, no accounts, no
network, no build step, no new dependency. The cost is that multi-user workflow,
assignment and notification come later (or never). The viewer's geometry code and
markup are untouched: the tab strip wraps them, and a page without `app_view.json`
still renders exactly as before. Divergence risk between `state.json` and the view
model is handled by one translation point (`app/view.py`) plus a golden test.
**Validation.** `docs/app-local-multitab.md` §20 defines the milestones; M2's
acceptance test is that a regenerated `viewer.html` behaves identically and a run
without `app_view` shows only the Viewer tab; M4's acceptance test is one real JBL
run driven end to end from the Workflow tab.
